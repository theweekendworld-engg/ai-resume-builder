01 The one idea

Everything below is downstream of a single sentence, so it is worth stating precisely.

Patronus keeps the evidence-backed record of what someone actually did, and everything else is generated from that record. The resume, the review packet, the promotion case, the monthly summary — none of them is a separate document you write. Each is a different view over the same confirmed wins.

That is why the numbers agree with each other, and it is the whole moat. A tool that only shows up at job-search time starts from a blank page and your memory. This one starts from years of dated, sourced evidence.

The load-bearing write

Confirming a Win writes Evidence(confirmedByUser=true) and ClaimLink(grounded) in one transaction. That single write is simultaneously the retention loop and the moat. Un-confirming must fully reverse it, including the Qdrant vector. Any refactor that decouples those two breaks the product thesis, not just a feature.

02 The whole system

Four places a user can be, one backend, one database.

The important asymmetry: the app calls server actions directly (they are functions), while the extension goes over HTTP to /api/extension/*, because a Chrome extension is a different origin with no Clerk session cookie. It carries a bearer token instead.

03 The data spine

Roughly forty tables exist. Six of them matter for understanding how anything works.

How a Win comes into existence

Sensitivity is a query concern

Any retrieval feeding an external artifact — a resume, a cover letter, an application answer — filters sensitivity = 'shareable' in the SQL. We never instruct a model to "skip confidential content". Prompts are advice; a WHERE clause is a guarantee. Tests assert the filter, not the output.

04 Two gates: flags and plans

Every feature passes two independent checks, and confusing them causes most of the "why can't I see this" questions.

Flags — src/lib/flags.ts

Postgres-backed, one row per flag, 60-second in-process cache. Resolution order inside decideFlag:

  1. No row at all → false. This is checked before the allow-list, so a missing row is off for everyone including admins. Rows are seeded on boot by src/instrumentation.ts.
  2. On the allow-list → true, even if disabled. This is how the team sees an unreleased feature.
  3. Disabled → false.
  4. Rollout ≥ 100 → true; otherwise a stable FNV-1a hash of (userId, flagKey) decides, so a user never flickers in and out.
The trap

enabled: true with rolloutPercent: 0 is off for everyone outside the allow-list. Both fields have to be set. The admin panel shows a "live" pill only when both are right.

Entitlements — src/lib/entitlements.ts

Two shapes. Feature gates are booleans from PLAN_FEATURES (does this plan include Radar at full depth?). Metered actions are counters in UsageQuota, consumed atomically by gateMeteredAction — a conditional updateMany that only increments while strictly under the limit, so concurrent calls cannot overshoot.

How the surfaces link to each other

Known gap

The resume's gap report says "nothing on your resume answers X" but does not yet link into the Work Log to capture that evidence. Closing that loop is the single highest-value connection still missing — it is the one place the resume would feed the log rather than only read it.

06 Resume generation

Eight steps, in the order a person actually works. The interesting one is step 3.

Why selection is a greedy set-cover

Two passes. First, walk the must-haves and then the stated duties, and for each one take the strongest unclaimed line that answers it. Only then fill the remaining slots by raw strength. A merely impressive bullet loses to a less impressive one that answers something the employer asked for — because the resume's job is to answer the posting.

The score

Coverage, not keyword overlap. The share of stated requirements answered by a line the candidate actually has. It cannot be gamed by adding keywords, and it goes down when the resume gets worse — drop the mentoring bullet and the mentoring requirement goes unanswered. The old ATS score scored a resume with ten fabricated skills at 95/100.

Coverage sees three sources of evidence, which is what stops it lying:

  • Kept bullets — what is on the page.
  • Credentials — education and the skills section. Without this, a career switcher was told "nothing answers: Bachelor's degree" while holding one.
  • Cut lines — evidence they have that did not fit. Reported as "you have this and it did not fit — put the line back", never as a gap.
No fabricated quantities

No generated artifact may contain a number, scope or outcome absent from its source. Enforced by the numeric guard in src/lib/ai/guard.ts on every writing call, with the candidate's own words as the source text. Zero fabrications is the pass condition — not "a low rate".

Three processes that cannot call each other's functions, only pass messages. Most extension confusion is really confusion about which of the three you are in.

Permissions — and why this shape

The manifest declares nine job-board hosts, not <all_urls>. Chrome renders <all_urls> to the user as "Read and change all your data on all websites", which is an absurd install prompt for a product whose brand is not taking more than it needs — and a Web Store review risk.

Learned the hard way

Narrowing the permissions without building that grant flow made the extension dead on any unlisted board, with "Re-scan this page" as the only button — and it cannot work, because there is no content script to answer. If you ever narrow a permission, ship the way to widen it in the same change.

Response shape

Every reply is { ok: true, data } or { ok: false, error }. Check both ok and data. A service worker that restarts mid-flight can answer ok with nothing, and trusting ok alone put a null plan into React state and took the whole panel down to a white screen.

09 Background work

One hourly cron, a Postgres queue, and a strict rule about fan-out.

Handlers fan out, never loop

A handler that would process N users enqueues N child jobs and returns. Vercel's function timeout makes this mandatory, not stylistic. And idempotency is a database constraint, not a convention: Job.dedupeKey, Win.signalId, WeeklyDigest(userId, weekStart) and CaptureSignal(sourceId, externalId) are all unique, so a double-fired cron is a no-op.

Email has a hard ceiling

Three outbound messages per user per week, enforced inside sendEmail so no feature can route around it. Transactional mail (a magic link) is exempt — suppressing an account-access link locks someone out with no recovery. Adding an email category means giving it a ceiling in CATEGORY_CEILING and a priority rank.

10 Four journeys

The same system, walked end to end, the way a person meets it.

A · Stranger → first resume

B · The weekly loop

GitHub PRs land as CaptureSignal → draftWins turns them into drafts → Friday's digest emails the drafts → one click per Win confirms it → Evidence + ClaimLink written → the resume, the packet and the Month in Review all silently get better. The user never writes anything. That is the whole design: every brag-doc tool that asks you to sit down and compose fails, because almost nobody sustains it.

C · Applying with the extension

D · Hitting a wall and paying

Free gives a few real uses of everything built. The tenth tailored resume exhausts a lifetime cap, so gateMeteredAction throws an EntitlementError carrying the paywall payload — their real numbers, their real plan — and the copy says "You've used all 10 Tailored resumes on Free — Career continues them." Because the counter is lifetime, there is no next month to wait for, which is what makes it an upgrade prompt instead of a pause.

11 Rules that must not break

Each of these has already been violated once and cost something. They are enforced by tests or grep gates, not by memory.

1 · Fail closed on truth

A claim that cannot be positively grounded resolves to needs_confirmation, never grounded. Errors and timeouts resolve down.

2 · No model IDs, no thinking budgets, no sampling numbers at call sites

Everything resolves from a per-task map in src/lib/config.ts and src/lib/ai/tasks.ts. A call site names a task: generateStructured({ task: 'winDraft' }).

3 · Every model call goes through generateStructured

So validation, retry, cost logging and the numeric guard happen once, consistently. One grandfathered exception — usageTracker.ts owns the raw call and is the floor of the stack, not a call site.

4 · Sensitivity is filtered in SQL, never in a prompt

See §3. Tests assert the WHERE clause, not the model's output.

5 · No raw Tier enum in the UI

always_on displays as "Career", pro as "Search". A journey test scans every user-facing string for leaked enum values and has caught real ones.

6 · Never delete user records on downgrade

Free-tier history is hidden, never removed, and the copy says so. It is the sentence that makes leaving safe, which is what makes coming back possible.

7 · Tests borrow shared state, they do not keep it

The suite runs against the database a human develops on. A test that flips a feature flag and walks away makes a feature vanish from your machine with nothing failing. flagHygiene.test.ts enforces this.
